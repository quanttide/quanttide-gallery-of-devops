# 提交与锁

提交环节最容易卡住的三件事：查暂存的命令不顺手、`.git/index.lock` 残留、并行会话在同一工作树里互相覆盖。处理原则一致——先判断状态，再动文件。

三条都发生在本地，不涉及远端：先用 `git status` / `git diff --cached` 把状态看清楚，再决定是否删锁、是否提交。

## 查全量暂存内容

现象：本机 git 没有 `status --staged` 这一用法，想确认暂存区收了哪些文件时没有直接可用的命令。

做法：改用下面任一命令查全量暂存，两者都不依赖 `status --staged`。

```bash
# 列出暂存区里的全部文件，只出文件名，便于脚本核对
git diff --cached --name-only

# 短格式状态，一眼区分暂存与未暂存
git status -s
```

只关心「暂存了哪些文件」用前者，还要看工作区状态用后者。

## `.git/index.lock` 已存在

现象：git 操作提示 `.git/index.lock` 已存在，写操作被挡住。

因：这把锁既可能是上次异常退出留下的陈旧锁，也可能是此刻确实有 git 进程在运行；不加区分就删，会破坏正在写入的索引。

做法：删锁是最后一步，前面的核对不能省。按顺序核三件事：

1. mtime 多久
2. 是否 0 字节
3. 有无运行中的 git 进程

三者都指向陈旧锁，再删掉重试；只要还有 git 进程在跑，就继续等。

## 并行会话在同一工作树提交

现象：同一工作树有并行会话在提交，后动手的一方容易把别人的改动一并带走。

因：提交前 `.git status` 已显示 `M <file>` 这类信号，说明工作区里混着其他会话正在改的文件。

做法：看到 `M <file>` 必须先看内容，确认归属后再提交。直接 `write` 会覆盖别人的提交——此时宁可先停手，把改动归属弄清楚再继续。

提交前的 `.git status` 是最省事的检查点，信号在提交动作之前就已经出现。

## 常见错误

| 现象 | 原因 | 处理 |
|------|------|------|
| 本机 git 没有 `status --staged` | 该用法不存在 | `git diff --cached --name-only` 或 `git status -s` |
| 报 `.git/index.lock` 已存在 | 陈旧锁残留，或有 git 进程在跑 | 核 mtime、是否 0 字节、有无运行中的 git 进程，三者都指向陈旧锁再删掉重试 |
| 提交内容混入他人改动 | 并行会话共享同一工作树 | `.git status` 出现 `M <file>` 先看内容，不直接 `write` |
